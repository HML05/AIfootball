> **一句话**：以五大联赛的真实数据为基础，用 XGBoost 做比赛结果预测，并在其上自建中文全文检索与「意图 → 工具/检索 → 作答」问答编排，最终交付一个带完整认证、实时比分与自动化回归体系的 Web 系统。

## 1. 项目背景与目标

### 1.1 要解决的问题

1. **足球数据分散且脏**：赛果、赛程、身价、伤病、xG 分散在多个源，命名与口径不一致（同一支球队在库里可能有 3 种叫法）。
2. **预测容易自欺**：数据泄漏（用未来信息预测过去）、以及把「命中率」和「样本外准确率」两种口径混着说，是这类项目最常见的两个坑。
3. **"能看"≠"能问"**：系统沉淀了 181 万条数据，但使用者只能看固定页面；而直接把问题抛给通用大模型，它会编造比分与身价。

### 1.2 目标与非目标（先说清楚）

| 类别 | 内容 |
|---|---|
| **做了** | 数据采集与清洗闭环、可复现的样本外模型评估、19 条路由的完整 Web 产品（含认证与权限）、自建中文检索与可溯源问答、自动化自检与部署交付 |
| **没做（诚实标注）** | 向量召回与重排（阶段 2）、逐场首发/位置级球员数据、超参搜索（Optuna）、多租户与高并发（当前单 worker）、生产级监控告警 |
| **能力上限（如实说）** | 足球低得分、高偶然，样本外准确率现实上限就在 **50% 上下**（仅比"全押主胜"高约 5.7pp）。任何「命中率 60%+」的宣传都值得质疑 |

### 2.2 两次典型请求的完整链路

**（1）打开「预测」页**：浏览器 → `GET /api/ui/predictions`（带会话令牌）→ 闸门校验 → SQLAlchemy 聚合查询（比赛 + 预测 + 球队）→ 组装 JSON（含模型版本与概率）→ React 渲染卡片与概率条。

**（2）提问「皇马和巴萨谁赢」**：
```
问题 → 意图识别（6 类关键词）→ 实体识别（中文别名表 240 支球队 + 4,745 名球员）
     → 并行/择一：6 个结构化工具（查库） + FTS5 检索（19,800 条语料）
     → 材料编号（[1]…[n] 与 sources 一一对应）
     → 作答：有 LLM key → 大模型按「材料里没有就说没有」作答；无 key → 检索摘要降级
     → 返回 {answer, sources, plan.steps, timing}
```

## 3. 数据层

### 3.1 数据源

| 数据源 | 用途 | 采集方式 |
|---|---|---|
| **football-data.co.uk** | 历史赛果（训练主数据） | 免 key CSV |
| **Understat** | 每场**官方 xG** | 免 key JSON 接口 |
| **API-Football (RapidAPI)** | 实时比分、球队/球员详情 | 免费层 100 次/天，带本地缓存 |
| **Football-Data.org** | 赛程与积分榜 | 免费层，10 次/分钟（脚本 7s 间隔） |
| **Transfermarkt**（salimt 开放数据集 + REEP 映射） | 阵容身价、转会、伤病、赛季数据 | 免登录镜像 + 一次性导入 |
| **TheSportsDB** | 队徽、球场、成立年 | 免费 key |
| **球小策（qiuxiaoce）** | 中文赛程与中文球员名 | 限速 2.1s/次 + 429 退避；未配 Token 时自动切换确定性演示赛程 |

### 3.2 数据规模（实测）

| 指标 | 数值 |
|---|---|
| 库体积 / 表数 / 行数 | 158.8 MB · **36 张业务表**（+1 张 SQLite 内部表）· **1,811,915 行** |
| 比赛 | 12,698 场（已完赛 11,315 / 待赛 1,379，赛程至 2027-05） |
| 联赛 · 球队 · 球员 | 10 · 240 · 4,745（其中 2,506 名有身价时序） |
| 身价时序 / 球员赛季数据 | 约 90 万行 / 约 37 万行 |
| 官方 xG 覆盖 | 9,007 场（自有代理 xG 覆盖 9,026 场，为官方的约 84 倍） |

### 3.3 数据工程要点

- **幂等 upsert**：以（联赛 + 日期 + 主客队）为键，存在则更新比分/状态，否则插入，可反复执行不产生重复。
- **队名规范化**：别名表 + 去重音 + 去俱乐部词（FC/CF/SC…）+ 互相包含匹配，解决「同队多名」；处理完再**清理孤儿球队**（既不属任何比赛也不属任何积分榜）。
- **跨源去重**：同一球员的中文行（球小策）与英文行（Transfermarkt）按 ID 桥接合并为一行，输出去重报告。
- **配额与限速**：所有付费脚本支持 `--budget`（达到上限自动停止）与 `--dry-run`；本地缓存 60 秒内同请求不扣点数。
- **合规**：只使用公开/免费接口与开源数据集；未购买官方 xG（全量约 ¥530），改用自建代理 xG 替代（见 §4.5）；不采集个人信息。

## 4. 模型层

### 4.1 特征工程（收益最大的一步）

| 版本 | 维度 | 新增内容 |
|---|---|---|
| v1 | 31 | Elo（5）、近期状态（12）、主客场（6）、历史交锋（4）、攻防效率（6）、联赛排名（3） |
| **v2（线上主模型之一）** | **90** | v1 + 射门/射正/角球/犯规/红黄牌（近 5/10 场与累计）+ 休息天数 + 7 天赛程密度 + 历史交锋统计 + 联赛标识 |
| v3 | 106 | v2 + **代理 xG**（泊松回归拟合） |
| **v7（线上集成成员）** | **126** | v2 + **官方 xG**（Understat）+ **Transfermarkt 阵容身价与伤病天数** |

**防数据泄漏的两条硬约束**：
1. Elo 按时间顺序逐场递推，每场只记录**赛前** Elo，赛后再更新；
2. 所有累计/滚动统计先 `groupby(team).shift(1)` 再 `cumsum/rolling`，永不包含当场与未来。

**训练/推理一致性**：线上不另写一套特征代码，而是把待预测比赛作为"占位行"追加到历史末尾，用与训练**完全相同**的函数算特征再取占位行向量。

### 4.2 评估协议

- **walk-forward 步进式样本外**：训练 `< 2025-08-01`（6,534 场），测试 **2025-08-15 ~ 2026-09-03（1,817 场）**，测试集完全不参与训练。
- 对照基线：**全押主胜 44.36%**。
- 稳健性：另在 4 个时间切点上重复评估，避免"单一切点运气"。

### 4.3 主要结果（同一测试集 1,817 场）

| 方案 | 特征数 | 准确率 | 宏 F1 | LogLoss | vs 基线 |
|---|---|---|---|---|---|
| 全押主胜（基线） | — | 44.36% | — | — | — |
| v1 | 31 | 47.00% | 0.3889 | 1.0805 | +2.64pp |
| **v2** | 90 | **50.03%** | 0.4007 | 1.0525 | +5.67pp |
| v3（+代理 xG） | 106 | 48.43% | 0.3961 | 1.0456 | +4.07pp |
| **v7**（+官方 xG + TM） | 126 | 49.70% | 0.3985 | **1.0292** | +5.34pp |
| **v9 = 集成 v2 + v7（等权概率平均，线上）** | 90+126 | **50.14%** | 0.3985 | 1.0338 | **+5.78pp** |
| 深度学习对照：DL-MLP（同 v7 特征） | 126 | 51.90%（单切点） | — | — | 4 切点均值 52.52% |

**三条结论**：
1. 特征工程收益最大（v1 → v2 准确率 +3.03pp，LogLoss 1.0805 → 1.0525）；
2. **更好的概率 ≠ 更高的命中率**：官方 xG 让 LogLoss 降到最低（1.0292）却不提升硬判准确率；
3. 集成是最优组合：v2（结果导向）与 v7（过程质量）互补，准确率最高且概率质量明显优于 v2。

### 4.4 概率校准与平局处理

平局最难预测（数据集占比约 24%）。做法：类别权重（逆频率）+ 在训练集内用时间序列 CV 选出**平局阈值 τ=0.36**；该配置把平局召回从 3.5% 提到 10.5%，代价是整体准确率略降 —— 因此线上同时给出「概率」与「倾向」两个输出，而不是只给一个硬判。

### 4.5 代理 xG（数据工程创新点）

官方 xG 在免费源中基本缺失（库内仅 108 场）。做法：用库内 9,026 场射门类统计，通过**泊松回归**拟合「射门统计 → 进球数」：

```
λ = exp(β0 + β1·射门 + β2·射正 + β3·角球 + β4·犯规 + β5·牌
        + β6·对手射门 + β7·对手射正 + β8·主场 + β9·联赛)
```

| 结果 | 数值 |
|---|---|
| 训练样本 | 18,012 条（球队-比赛） |
| 验证集 MAE | **0.7358**（基线 0.9669，降低 24%） |
| 与官方 xG 相关性 | 主队 0.627 / 客队 0.542 |
| 覆盖率 | 9,007 场（官方的约 84 倍） |

**诚实结论**：代理 xG 提升概率质量与平局召回，但降低硬判准确率，因此线上以 v2/v7 为主，代理 xG 用于覆盖广度与概率型场景。

### 4.6 预测闭环与两类口径

```
① 生成预测 predict_upcoming_v2(days)  → 写 predictions（概率 + 特征快照，match_id 唯一索引保证幂等）
② 赛后回填 backfill_results()          → 比赛 FT 后写入 actual_result 与 hit 标记
③ 复盘统计 review_stats()              → 总体/分联赛/分类型命中率
④ 历史回测 predict_backtest(区间)      → 批量回测落库（is_backtest=1）
```

**口径必须分开说**：命中率 = 全部已评估预测（含回测，1,752 条）的命中比例；准确率 = 生产模型的样本外准确率（1,817 场）。两者样本不同，**不能直接比较**——界面上也标了这一处定义。

## 5. 服务层

### 5.1 接口设计

- **`/api/ui` 21 条聚合路径 / 22 个方法**：按「一页一次请求」设计，页面不需要自己拼多个接口。
- OpenAPI 全量 **56 条路径 / 60 个方法**（其中 `/api/ui/*` 22 个方法、`/api/auth/*` **19 个方法**、`/api/teams|matches|predictions|players|leagues` 14 个、`/api/agent/*` 3 个、`/health` 与根路径 2 个；WebSocket 实时推送不占路径）。
- 统一响应结构：列表接口带分页与筛选参数；检索/问答带 `sources` 溯源字段。

### 5.2 认证与权限

| 能力 | 实现 |
|---|---|
| 密码存储 | 自研 PBKDF2（加盐迭代），不存明文 |
| 会话 | 服务端会话令牌（Bearer），支持过期与主动踢下线 |
| 登录方式 | 账号密码 + **扫码登录**（一次性票据） |
| 自助注册 | 新账号固定 `user` 角色，`AUTH_ALLOW_REGISTER=false` 可关闭 |
| 忘记密码 | 两步式：申请一次性 6 位重置码 → 设新密码并**踢掉旧会话**；默认不回显码（写 `logs/auth_reset.log`），公网安全 |
| 权限 | 管理端 4 页签与写操作需管理员角色；非管理员访问返回 403/卡住入口 |
| 账号设置 | 顶栏头像点开：改昵称 / 账号名 / 手机号（`PATCH /api/auth/profile`）、上传头像（`POST /api/auth/avatar`，后端居中裁方 + 只缩不放，落 `data/uploads/avatars/`）、删除头像、改密码（改完踢掉其它会话，当前会话保留）；头像图 `GET /api/auth/avatar/{user_id}` 故意不鉴权（`<img src>` 带不了 Authorization），带 ETag + 版本号防缓存 |
| 闸门 | 未登录访问任何页面 → 整页跳转登录页；未登录调接口 → 401 |

### 5.3 定时任务（APScheduler，5 个）

| 任务 id | 作用 | 触发 |
|---|---|---|
| `daily_fixtures` | 同步赛程 | 定时 |
| `daily_predict` | 生成未来预测 | 定时 |
| `live_poll` | 轮询实时比分（并在赛后触发回填） | 间隔 |
| `weekly_stats` | 更新周度统计 | 定时 |
| `transfer_update` | 更新转会与身价 | 定时 |

### 5.4 性能与容量取舍

- 聚合查询在 181 万行规模下为**毫秒级**；写压力集中在 5 个定时任务，因此部署定为**单 worker**（避免 SQLite 并发写锁竞争）。
- SQLAlchemy 抽象在位：换 Postgres 只需改 `DATABASE_URL`（未做，属后续规划）。

## 7. 检索与智能问答（RAG）

### 7.1 阶段 0：中文全文检索层（自建）

**为什么自建**：SQLite 内置 `unicode61` 分词器对中文**完全失效**（查「马德里」0 命中），`trigram` 对 2 字词失效；上 Elasticsearch 对单机项目过重。

**方案**：FTS5 + jieba 双向分词（写入与查询同源分词），索引本地自建。

| 指标 | 实测 |
|---|---|
| 语料 | **19,800 条 / 17.8 MB**（12,698 场比赛 + 4,745 名球员 + 1,803 条预测 + 304 段项目文档 + 240 支球队 + 10 个联赛） |
| 建索引耗时 | 4.9 s（服务器可重建，索引不入库） |
| 查询延迟 | **2~11 ms**（平均约 1.9 ms） |
| 评测对比（查「马德里」） | unicode61：**0 命中**；trigram：0 命中；本方案：**518 条** |
| 其他评测 | 「曼城」1 条 · 「Bayern Munich」1 条 · 球员名「梅利耶」1 条 · 文档词「部署」19 条（命中到行号） |
| 溯源 | 每命中带 `source`{表, 主键, 站内 URL}，自检逐条回主库核对 |

接口：`GET /api/ui/search?q=&kind=&limit=`、`GET /api/ui/search/stats`；自检 `scripts/verify_search.py`（23 项）。

### 7.2 阶段 1：智能问答层（自研三步编排）

| 环节 | 实现 |
|---|---|
| 意图识别 | 6 类（胜负预测 / 积分榜 / 球队画像 / 近期状态 / 球员信息 / 历史交锋），关键词 + 中文别名实体识别 |
| 工具层 | 6 个结构化工具（`team_info` / `team_form` / `head_to_head` / `league_table` / `match_prediction` / `player_info`），统一返回 `{summary, data, sources}`，纯 Python 函数、可单测；**不依赖 langchain**（旧 `initialize_agent` 在 langchain 0.2+ 已废弃） |
| 检索 | 复用阶段 0 的 FTS5 检索，作为材料补充 |
| 作答 | 有 key → 大模型按 `SYSTEM_PROMPT` 五条硬规矩作答（材料里没有就说没有）；无 key → **自动降级**为「库内事实 + 检索片段」，界面显示 `mode=retrieval`，不假装生成 |
| 溯源 | 答案里的 `[n]` 与 `sources` 一一对应，可点回站内原始页面；自检会逐条回主库核对，曾借此抓到一个**幽灵引用**（`predictions` 是 `WITHOUT ROWID` 表、主键是 `pred_id`，早期写成 `match_id` 会指向错误记录） |

**实测延迟**：检索摘要模式 **84~139 ms**（热运行；冷启动首次约 0.66 s，其中工具 68~95 ms、检索 12~22 ms）；接入 `deepseek-flash` 大模型模式约 **2.7 s**（含推理 token）。

**踩过的一个真坑（推理模型静默截断）**：`deepseek-flash` 是推理型模型，会先输出 `reasoning_content`，而**推理 token 同样占用 `max_tokens` 预算**——预算不足时 `content` 被切成半句话而 HTTP 仍是 200。修法：识别 `finish_reason=length`（而不只是看请求是否失败）并用双倍预算自动重试一次，仍被截断则在响应里明确标注。`scripts/check_llm.py` 可体检配置与账号可用模型。

接口：`GET /api/ui/ask/status`、`GET|POST /api/ui/ask`；自检 `scripts/verify_qa.py`（37 项）+ `scripts/verify_ask_ui.py`（17 项，浏览器）。

### 7.3 边界（如实）

- 只做**单轮**问答，不做多轮对话与上下文继承；
- 未接向量召回与重排（阶段 2 规划），当前是「关键词意图 + 结构化工具 + FTS5」的组合；
- 数值类问题全部走工具与数据库，**不以模型记忆作答**；
- 未配 LLM key 时功能完整可用（降级模式），界面如实提示。

### 8.2 六条可复用的工程教训

1. **跑着的服务可能是旧代码**：uvicorn 未开 `--reload` 时，改完 `src/` 必须重启才算数。曾因此把「新写的字段不存在」误判为前端 bug——判断依据是接口返回的字段集。
2. **Playwright 的 locator 是实时的**：`locator.count()` 必须在点击**前**取成整数快照，否则前后都读到点击后的 DOM（表现为「筛选前 0 → 筛选后 0」的假失败）；另外顶栏导航与页内按钮同名时要用更精确的选择器。
3. **同源优先**：控制台页面里接口地址一律同源优先（否则公网 HTTPS 页面会去请求 `127.0.0.1:8000`），已用假域名（http/https × 5 页）自动验证。
4. **玻璃态容器里的弹层要用 portal**：`backdrop-filter`（以及 `transform` / `filter`）会让元素成为 `fixed` 后代的 containing block。账号设置弹层一开始挂在顶栏内，`fixed inset-0` 被限制在顶栏那条胶囊里——画面看着像「弹层被顶栏截断」，Playwright 直接报 `element is outside of the viewport`；改成 `createPortal(…, document.body)` 并让遮罩的 `z-index` 低于顶栏（`z-30` < 顶栏 `z-40`，否则遮罩排在后面会挡住菜单按钮）后才正常。同理，`FormData` 上传时不能统一写 `Content-Type: application/json`——手工设置会让浏览器丢掉 multipart boundary，后端返回 422「file 字段缺失」。
5. **自检脚本要主动清掉环境变量，也别依赖 `env`**：容器入口脚本自检本机 18/18，一进 CI 就挂 2 项——场景「没配数据包地址」没有清掉环境里的 `DATA_PACK_URL`（CI 里是 job 级变量），于是它又下了一次数据包、警告不出现；把 `env PATH=… sh …` 换成子 shell 里 `export` 时又踩到第二个坑：本机 `~/.local/bin/env` 是 uv 装的一个 328 字节 PATH 包装脚本，登录 shell 下排在 `/usr/bin/env` 前面，整条子命令静默无输出（15 项假失败）。结论：自检要显式声明它依赖的变量，跨环境跑一遍才算数。
6. **同一份自检在 Windows 与 Linux 上能验的东西不一样**：给云主机直装脚本写自检时，`chmod 600 .env` 这条在 Windows 的 Git Bash（MSYS）上是空操作 —— `stat -c %a` 恒返回 644，而同一句在 Linux 上会真的生效。硬按一个标准写，等于让这条断言在一个平台上永远假失败（或永远假通过）。做法是把断言写成**按平台分流但只算一条**：Linux 查权限位本身，其它平台查「脚本确实调用了 `chmod 600`」，这样两边计数一致、CI 里补上真正的权限位校验。这条断言第一次进 CI 就挂了 —— 原因在自检自己身上：`chmod` 也被桩成了「只记日志」，于是 Linux 分支永远看不到 600（本机 Windows 分支查的是调用记录，所以一直绿）。桩要「记日志 **并且** 真调用 chmod」才对。同理，凡是「装系统包 / 写 systemd / 起内核级资源」的脚本，本机只能用桩命令验行为，第一次真跑一定发生在真服务器上——这一点要在文档里写明，不能拿桩自检冒充真机验证。
