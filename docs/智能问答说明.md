# 智能问答说明（RAG 阶段 1）

> 一句话：把「自然语言问题」翻译成**库内查询 + 全文检索**，再用大模型（可选）组织成**每句可溯源**的答案；
> 没配 LLM key 时自动降级为「检索摘要」，仍然只讲库里的数字，绝不编造。

- 接口：`POST /api/ui/ask`、`GET /api/ui/ask`（curl 调试）、`GET /api/ui/ask/status`
- 页面：前端 `/ask`（检索 + 问答两个页签）
- 自检：`python scripts/verify_qa.py`（37 项，需要 API 在 8000 端口运行）
- 与阶段 0 的关系：检索层（`docs/检索层说明.md`）提供证据片段；本层负责**意图识别 → 工具调用 → 编排 → 引用**

---

## 1. 为什么要重写一遍（旧的 `src/agent/` 是死的）

项目里原本有一套 langchain Agent（`src/agent/tools.py` 六个 `@tool`、`src/agent/agent.py` 的
`initialize_agent(... AgentType.OPENAI_FUNCTIONS ...)`、`src/api/agent.py` 三个接口），实测**根本跑不起来**：

| 问题 | 实测 |
| --- | --- |
| 依赖没装 | `langchain` / `langchain-openai` / `openai` 在 `pip list` 里都不存在（只有 numpy/pandas/sklearn/torch） |
| API 已废弃 | `initialize_agent`、`langchain.chat_models.ChatOpenAI`、`langchain.memory` 在 langchain 0.2+ 已迁到 `langchain-classic` / `langchain-openai`，装上旧代码也是坏的 |
| 没有密钥 | `.env` 里 `LLM_API_KEY` 为空 → `POST /api/agent/chat` 永远 `503 AI Agent未初始化` |
| 数字口径错 | 旧工具把 `players.market_value`（原始欧元）当「万欧元」打印，答案会差 1 万倍 |

结论：与其装一堆用不上的依赖去救旧代码，不如**自己写三小步编排**（意图 → 工具/检索 → 生成），
只依赖 `requests`（项目已有），可测、可控、可解释。

## 2. 数据流

```
用户问题
   │
   ├─ router.plan(q)          关键词 → intent；别名/中文名 → 实体（球队/球员/联赛）
   │                           产出 steps=[{tool,args,reason}]，每步都带「为什么调它」
   ├─ router.run_plan(steps)  执行 6 个工具（只读主库），单个工具失败不影响其它
   ├─ router.search_query(q)  问题去掉疑问词 + 拼上实体名 → FTS5 检索得到片段
   │
   ├─ build_context(...)      把「工具事实」和「检索片段」编号成材料
   ├─ llm.chat(...)           有 LLM_API_KEY → 让模型只依据材料作答，句末标 [n]
   │                          没有 key / 调用失败 → digest_answer() 直接用事实拼出检索摘要
   └─ 返回 {answer, mode, intent, plan, facts, sources, search, missing, timing, llm}
```

**`mode` 只有两种取值**：`llm`（大模型作答）与 `retrieval`（检索摘要）；`missing[]` 会如实说明
「为什么不是大模型作答」「索引是不是没建」。

## 3. 六个结构化工具（`src/qa/tools.py`）

全部是**纯函数**（不依赖 langchain、不用 ORM），只读 `data/database/football.db`，
返回统一结构：`{"tool","ok","summary","data","sources":[{"table","id","label","url","ref"}]}`。

| 工具 | 入参 | 数据来源 | 说明 |
| --- | --- | --- | --- |
| `team_info` | 球队（中文别名/英文名/队名片段） | `teams` + `standings` + `players` | Elo、阵容人数、总身价、平均年龄、最近赛季名次与积分 |
| `team_form` | 球队, n=5 | `matches` | 近 n 场胜负与比分（**同场次重复采集已折叠**） |
| `head_to_head` | 两队, n=10 | `matches` | 历史交锋明细 + 胜平负统计 |
| `league_table` | 联赛, limit=10, season | `standings` + `teams` | 默认取该联赛**最大 season**（当前赛季） |
| `match_prediction` | 主队, 客队 | `predictions` + `matches` | 优先未开赛比赛的落库预测；没有则给最近一次已完赛并对比实际结果 |
| `player_info` | 球员 | `players` + `player_radar` + `tm_player_seasons` | 位置/年龄/国籍/身价 + 雷达聚合（出场、进球、身价分位）+ 最近赛季 |

要点：

- **别名表**：`teams` 表只有英文名，靠 `data/reference/team_alias_zh.json`（240 队中文名与简称）才能听懂「皇马」「巴萨」「大巴黎」。
- **金额**：`market_value` 是原始欧元，`money()` 统一格式化成「万欧 / 亿欧」，修掉旧工具差 1 万倍的口径错误。
- **浮点**：`player_radar` 里出场数/分钟是浮点，`_int()/_round()` 把「55.0 场」修成「55 场」。
- **重复采集**：`matches` 里有同一场次被采集两条（日期差 1 天、比分相同）的情况，`_dedupe(window=3)` 按「同主客 + 同比分 + 日期相近」折叠，避免「近 5 场」里同一场出现两次。

## 4. 意图识别与实体识别（`src/qa/router.py`）

`KEYWORDS` 六类意图（`status` 里就是这六个）：

| intent | 触发词（部分） | 典型步骤 |
| --- | --- | --- |
| `predict` | 预测、胜率、概率、谁赢、赢面 | 预测 + 交锋 + 两队近况（4 步） |
| `h2h` | 交锋、交手、历史战绩、直接对话 | 交锋 + 两队近况 |
| `compare` | 提到两支球队但没问胜负 | 交锋 + 两队资料 + 近况 |
| `form` | 近况、状态、最近、连胜、连败 | 近况 + 球队资料 |
| `standings` | 积分榜、排名、榜首、降级、夺冠 | 积分榜（或先取球队名次） |
| `player` | 身价、进球、助攻、位置、出场 | 球员资料 |
| `team` | 主教练、主场、阵容、成立 | 球队资料 + 近况 |
| `search` | 以上都没命中 | 纯全文检索（不再编造） |

- 实体识别用**全量名字 + 中文别名**做最长匹配（`team_surfaces()` / `player_surfaces()` / `league_surfaces()`），
  并过滤 `ac/sc/fc` 这类会造成误判的超短名（`_STOP_SURFACES`）。
- `search_query()` 把疑问词/虚词（谁、多少、怎么样、最近…）去掉再检索——
  修之前「凯帕身价多少」会命中 4785 条无关记录，修之后命中 1 条。

## 5. 引用溯源（本层的核心卖点）

- `sources` 每条是 `{n, table, id, label, url, ref, via}`：**n 从 1 连续编号**，`via` 标明这条来自哪个工具或检索。
- 同一「表 + 主键」只出现一次（`collect_sources()` 去重）。
- 前端用 `url` 直接跳站内页面（`/matches/12641`、`/teams/60`、`/players/88`）。
- 自检会**逐条回主库核对** `(table, id)` 是否真实存在，防止「幽灵引用」。
  这一步真抓到一个 bug：`match_prediction` 曾把 `predictions` 的引用 id 写成 `match_id`——
  而 `predictions` 是 **WITHOUT ROWID** 表、主键是 `pred_id`，两个 id 并不相等，现已改为真实 `pred_id`。

## 6. 防幻觉与诚实原则

`SYSTEM_PROMPT` 五条硬规矩（材料里没有就说没有）：

1. 数字（比分、概率、积分、身价、排名、日期）必须逐字来自材料，不许自己算/估/编；
2. 每用一条材料，句末标出编号 `[1][3]`；
3. 材料里没有的信息，直接说「库内没有相关记录」并说明还缺什么；
4. 简体中文、先结论后依据、200 字以内、不复述系统说明；
5. 不提「工具」「材料」「prompt」等字眼。

没有 key 时不做「假装在生成」：`mode=retrieval`、`missing` 写明
「未配置 LLM_API_KEY：当前是『检索摘要』模式（库内事实 + 检索片段）, 在 .env 里填 key 后自动切到大模型作答」。

## 7. 大模型作答（已真机联调）

配好 `.env` 的 `LLM_API_KEY` 后 `mode=llm`，答案由模型**只依据材料**生成（第 6 节的五条硬规矩写进 `SYSTEM_PROMPT`）。
本机联调记录（`deepseek-flash`，2026-10-07）：

```bash
python scripts/check_llm.py          # 脱敏回显 key/base/model + 列账号可用模型 + 发一次真实 ping
# llm_ready=true model=deepseek-flash mode=llm
```

| 问题 | 结果 |
|---|---|
| 英超积分榜前 5 | 261 字结构化答案（积分 + 场次 + 净胜球），每段依据标 `[1]`，`llm_ms≈2.2 s` |
| 皇马和巴萨谁赢 | 122 字答案：分场次说明「最近一次交锋皇马 2-1 胜、2026-05-10 巴萨 2-0 胜」，并明确「库内没有尚未开赛比赛的确定胜负记录」，`llm_ms≈2.6 s` |

### 踩到的坑：推理模型的 token 预算会让答案被静默截断

`deepseek-flash` 是**推理型模型** —— 响应里除了 `content` 还有 `reasoning_content`，
而 `usage.completion_tokens_details.reasoning_tokens` **同样计入 `max_tokens` 预算**。
预算不够时服务端把 `content` 硬切成半句话，**HTTP 依然是 200**（`finish_reason=length`），
旧实现 `max_tokens=900` 且从不看 `finish_reason`，于是表现为「答案莫名断掉但不报错」。

现在的处理（`src/qa/llm.py`）：

1. `chat()` 返回体新增 `finish_reason` / `truncated`（`finish_reason == "length"`）/ `reasoning_tokens` / `retried`，默认预算提到 **1600**；
2. 只要 `truncated` 就用 `max(1600, 预算 × 2)` **自动重试一次**，重试内容更长才采用并置 `retried=True`（判据是 `truncated` 而不是 `ok` —— 推理 token 吃光预算时 `content` 可能是空的）；
3. 仍被截断时往 `missing[]` 追加说明（含本次推理 token 数），前端在答案卡片下如实显示。

复现验证（把预算压到 64 token 强制触发）：

```
[不重试 · 预算 64] ok=False finish=length truncated=True reasoning=64 len=0
[自动重试 · 预算 64] ok=True  finish=stop   truncated=False retried=True reasoning=191 len=74
```

> 账号可用模型用 `GET {base}/models` 查（本账号只有 `deepseek-flash` 与 `deepseek-v4-pro`）；
> `LLM_BASE_URL` 只填到域名（`https://api.deepseek.com`），`/chat/completions` 由代码自己拼，填整条路径会 404。

## 9. 自检（`scripts/verify_qa.py` 37 项 + `scripts/verify_ask_ui.py` 17 项）

```bash
python scripts/build_search_index.py     # 检索索引要先建好（否则 ask 里检索部分为空）
python scripts/verify_qa.py              # 后端 37 项；API 需在 8000 端口运行
python scripts/verify_ask_ui.py          # 前端 /ask 页面 17 项（Playwright 真点击，需先 python scripts/build_webui.py）
```

`verify_qa.py` 四段覆盖：

1. **工具层（14 项）**：中文别名找队、未知实体不抛异常、近况去重、交锋胜平负自洽、积分榜名次递增、预测概率和为 1、球员事实无浮点尾巴；
2. **意图与检索串（4 项）**：六类意图、去虚词、保留实体、无实体时非空；
3. **编排（9 项）**：`mode=retrieval`、答案由工具事实拼成（不是凭空生成）、引用编号连续、**引用逐条回主库核对**、timing、步骤理由、无 key 时的诚实说明（配了 key 时改为断言 `mode ∈ {llm, retrieval}`）、未知问题与空问题不炸；
4. **接口与闸门（10 项）**：GET/POST 未登录 401、status 与 `mode` 一致、六个工具、`/ask` 形状、`top_k` 越界 422、耗时 < 5s。

实测关键值：答案延迟 **84~139 ms**（无 LLM，热运行；冷启动首次约 0.66 s，含 3 条引用）；引用 19 条**全部**能在主库查到；
`predictions`/`matches`/`teams`/`players`/`leagues` 五类来源都已验证。

`verify_ask_ui.py` 三段覆盖（截图存 `%TEMP%\aifootball_view\ask\`）：

1. **检索页**：命中条数与分词模式来自接口（`292 matches · tokenizer jieba`）、分词结果展示、20 条结果链接、首条是站内路径（不带 `:8000`）、点「Predictions」筛选后 URL 带 `kind=prediction` 且结果变少；
2. **问答页**：`Ctrl/⌘+Enter` 提交「皇马和巴萨谁赢」后出答案、答案里带真实比分/百分比、`[n]` 引用、可折叠的执行步骤区块；
   模式徽标与提示条**按后端 `llm_ready` 自动切换断言** —— 未配 key 时断言 `Retrieval summary` 徽标 + 「未配置 LLM_API_KEY」提示条，配了 key 时断言「大模型作答」徽标 + `LLM_API_KEY` 字样消失（等待答案出现也按 15 s / 60 s 两档轮询）；
3. **页面质量**：无横向溢出、无坏图、控制台 0 报错。

> 写浏览器断言时的两个坑（都踩过）：顶栏导航里也有 `Teams` / `Ask` 按钮，用 `get_by_role("button", name="Ask")` 会点到导航导致页面跳走
> （改用不与导航重名的 `Predictions` 药丸、以及 textarea 的 `Control+Enter`）；Playwright 的 locator 是**实时**的，
> `count()` 必须在点击**前**取成快照，否则点击前后读到的是同一份点击后的 DOM。

## 10. 边界与已知限制

| 限制 | 说明 |
| --- | --- |
| 没有 key 时没有生成式回答 | 只能给「库内事实 + 检索片段」的摘要；`.env` 填 `LLM_API_KEY` 即自动切换 |
| 推理模型吃预算 | `deepseek-flash` 的推理 token 也计入 `max_tokens`，预算过低会截断（已自动加倍重试，见第 7 节）；问答耗时随推理长度升到 2~4 s |
| 不做多轮对话 | 每次问答独立，不保留上下文（旧 langchain 的 `ConversationBufferMemory` 未沿用） |
| 没有向量召回 | 只有 FTS5 词法检索；语义相近但换词的问法可能召不回（阶段 2 再上嵌入） |
| 别名覆盖 240 支球队 | 新球队需补 `data/reference/team_alias_zh.json` 后重建索引 |
| 球员中文名 2160/4745 | 其余球员只能用英文名或音译问（数据源本身没有中文名） |
| `matches` 有重复采集 | 工具层已折叠展示，但主库原始数据未清理（属采集链路问题） |
| 单 worker | 问答与检索都是同步阻塞 + SQLite，部署仍须 `--workers 1`（见 `docs/deploy.md`） |
| 检索 COUNT 在长查询上偏慢 | 「皇马和巴萨谁赢」这类多 token 查询 `search_ms` 约 0.5 s（1191 条命中做全量 COUNT） |

## 11. 与后续阶段的衔接

- **阶段 2（可选）**：中文嵌入模型 + `sqlite-vec`/FAISS 做语义召回，与 FTS5 做混合重排；
  语料可扩到赛前情报、赛制规则；问答侧可加多轮记忆与「按用户追问继续查」。
- **工具扩展**：新增工具只需在 `src/qa/tools.py` 写纯函数 + 注册进 `TOOLS`，
  再在 `router.KEYWORDS` 加触发词与 `plan()` 里加一个分支，`sources` 按统一结构返回即可。
- **接口侧**：`src/api/qa.py` 已按登录闸门挂载，新增接口沿用同一 `APIRouter(dependencies=[Depends(require_ui_login)])`。
