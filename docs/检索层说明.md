# 检索层说明（RAG 阶段 0）

> 目的：让"用自然语言问数据"这件事**落在真实数据上**，并且每一条结果都能溯源到具体记录或文档行号。
> 这一层不需要任何大模型 API / Key，是纯本地检索；后面接 LLM 编排就是完整的 RAG（见 §8）。

---

## 1. 为什么自己做分词

SQLite FTS5 内置的两个分词器在中文上都不可用（`scripts/verify_search.py` 会现场复现，不是我口头说的）：

| 分词器 | 语料 | 查询 | 命中 |
|---|---|---|---|
| `unicode61` | 皇家马德里主场逆转巴塞罗那 | 马德里 | **0** —— 整段中文被当成一个 token |
| `trigram` | 同上 | 逆转（2 字） | **0** —— trigram 要求查询 ≥ 3 字符 |
| 本方案（jieba） | 同上 | 马德里 | **518 条**（全库范围） |

所以：写入时用 jieba 把文本切成 token 存进 FTS5 的 `tokens` 列，查询时用**同一套口径**切分再 `MATCH`；
没装 jieba 时自动退化为字符 bigram（零依赖，两字词照样可召回）。索引里记了 `meta.mode`，
查询按索引记录的模式切分，避免"写入 jieba、查询 bigram"这种口径错配导致的漏召回。

## 2. 语料（19,800 条）

| 类型 `kind` | 条数 | 来源 | 命中后能跳转 |
|---|---|---|---|
| `match` | 12,698 | `matches` + 主客队名 + 联赛 | `/matches/{id}` |
| `player` | 4,745 | `players` + 所属球队 | `/players/{id}` |
| `prediction` | 1,803 | `predictions` + 比赛 + 概率/命中 | — |
| `doc` | 304 | `docs/*.md` 按标题分块，`ref` 形如 `docs/deploy.md#L261` | — |
| `team` | 240 | `teams` + 联赛 + 中文别名 | `/teams/{id}` |
| `league` | 10 | `leagues` | — |

**中文别名表** `data/reference/team_alias_zh.json`（240 支球队）：业务库里 `teams` 只有英文名
（`Arsenal` / `Man City`），用户却只会说「阿森纳」「曼城」—— 没有这张表，中文搜球队一律 0 结果。
别名只拼进**检索索引**的标题与正文，不改动业务库与页面显示。

## 3. 索引文件

* 路径 `data/database/search.db`，独立于业务主库 `football.db`，可随时删掉重建；
* 结构：`docs`（正文 + 分词结果 + 溯源字段）、`docs_fts`（FTS5 external content 表）、`meta`（分词模式 / 构建时间 / 主库路径 / 别名数）；
* 体积 **17.8 MB**、构建耗时 **4.9 秒**（19,800 条，jieba 模式）；文档类语料随 `docs/*.md` 增减自动变化，所以条数会浮动；
* 构建时先写 `search.db.tmp` 再整体替换 —— 服务端同时在查询时，读者只会看到"旧的完整索引"或"新的完整索引"，不会读到半成品。

## 4. 构建与自检

```bash
python scripts/build_search_index.py          # 重建索引（默认 jieba；--bigram 强制退化）
python scripts/verify_search.py               # 23 项自检（需要 API 已在 8000 端口运行）
python scripts/smoke_ui_api.py                # 28 个 /api/ui 端点冒烟（含检索两个）
```

`verify_search.py` 覆盖：语料规模与分词模式、**unicode61/trigram 问题复现**、中文与两字词召回、
球队/球员/文档检索、引用完整性（每条都有 `source.table/id/ref`，且抽查的 id 能在主库里查到）、
未登录 401、`kind` 过滤、空查询、单次查询耗时（实测 2.2 ms 热缓存 / 10.9 ms 冷启动，含连接建立）。

## 5. 接口

### `GET /api/ui/search`

| 参数 | 说明 |
|---|---|
| `q` | 自然语言或关键词，例：`皇家马德里 逆转`、`部署`、`拜仁` |
| `kind` | 可选，限定 `league/team/player/match/prediction/doc` |
| `limit` | 1–50，默认 10 |
| `offset` | 分页偏移 |

检索策略：先按 **AND**（所有 token 都要出现）查，0 结果再退化成 **OR**；排序 `bm25`，
标题里直接命中查询串的排前面；命中的中文片段在 Python 侧生成（`【关键词】` 高亮），比 FTS5 的
`snippet()` 可读 —— 因为 FTS5 只能对分词列做片段，返回的是被空格拆开的 token 串。

响应结构（节选真实返回）：

```json
{
  "query": "皇家马德里",
  "tokens": ["皇家", "马德里"],
  "operator": "AND",
  "mode": "jieba",
  "count": 290,
  "hits": [
    {
      "kind": "match",
      "ref": "match:9012",
      "title": "Real Madrid 4-1 Sociedad 皇家马德里 皇马 银河战舰 皇家社会",
      "snippet": "…【皇家马德里】 对阵 皇家社会 比分 4-1 日期 2026-04-12…",
      "score": 12.83,
      "source": {"table": "matches", "id": "9012", "url": "/matches/9012"}
    }
  ]
}
```

### `GET /api/ui/search/stats`

索引概况：`ready / total / by_kind / mode / mode_desc / built_at / main_db / size_bytes`。
索引不存在时返回 `{"ready": false, ...}`（不抛 500），`/search` 则返回 503 并提示先建索引。

两个接口都挂在 `/api/ui` 下，**复用界面接口的登录闸门**：未登录 → 401（`src/api/ui.py` 的 `require_ui_login`）。

## 7. 边界与已知限制

* **索引不会自动跟随数据更新**：定时任务写入新比赛/预测后，需要重跑 `scripts/build_search_index.py`
  （4.9 秒，可在任务里挂上；目前没挂，避免影响正在跑的调度）。
* 别名表覆盖 240 支球队的人工映射，冷门球队可能有更常见的译名没收录；缺别名时用英文名仍可搜到。
* 球员中文名只有 2,160 / 4,745 条（来自数据源），其余用英文名检索。
* 预测语料包含回测样本，`extra` 里带 `hit`，但**不含** `is_backtest`，需要区分时看 `ref` 对应的预测记录。
* 没有向量召回：同义改写的问法（「谁赢了」vs「比分」）靠 token 命中，不做语义泛化 —— 这是阶段 2 的事。

## 8. 与 RAG 阶段 1 / 2 的衔接

* **阶段 1（需要 `LLM_API_KEY`）**：`src/api/agent.py` 的 `/api/agent/chat` 目前恒返回 503
  （`langchain` / `openai` 都没装、`LLM_API_KEY` 为空，且 `initialize_agent` 这类旧 API 在
  langchain 0.2+ 已迁走）。计划改成用 `openai` SDK（DeepSeek 兼容）自己写工具循环：
  **意图 →（结构化工具 / 本层检索 / 并行）→ 组装上下文 → 生成**，回答强制带本层的 `sources`。
  `src/agent/tools.py` 里的 6 个数据工具先解耦成纯函数，再给编排层调用。
* **阶段 2（可选）**：中文嵌入模型 + `sqlite-vec` 做向量召回，语料扩到赛制规则与赛前情报，加一层重排。
